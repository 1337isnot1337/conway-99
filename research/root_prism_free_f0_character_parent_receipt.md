# Exact acceptance of a character-count candidate

This checker separates a native incumbent from an accepted count witness. It has no optimizer and imports no mathematical builder. It reads frozen protobuf archives and exact integer row matrices in sequence, releasing each large object before the next stage. Preparation checks source and input hashes plus small arithmetic controls; it has not checked a production candidate.

## Required checks

The candidate is a plain JSON array of 18,444 integers. Both its file hash and the hash of its canonical integer array are recorded. The checker verifies every final domain, every constraint in the 34,398-row final target, and every constraint in the 34,436-row original signed-character model. Native products and allowed tables are evaluated with Python integers. The original model restores obligations removed from the current native representation through previously proved table projections.

The first 15,038 values are orbit counts. The checker evaluates all 5,973 primitive equalities and 21,746 primitive inequalities, then independently checks all 903 population identities. For distinct selector orbits these identities sum the corresponding pair counts to the product of their populations. Within an orbit they sum to the population choose two. The 389 previously proved zero pair orbits contribute zero.

Each original orbit size is 3, 6, or 12. If its integer count is (n_j) and size is (s_j), its original fractional coordinate is (n_j/s_j). The checker restores the 15,200-coordinate parent at common denominator 12, using numerator (12n_j/s_j), and inserts the 162 proved zero edge coordinates. It then checks every one of the 28,043 original parent rows and all 25 original integer-refinement rows. Thus neither a native status nor a reduced-model-only evaluation is an acceptance condition.

The row matrices and restoration maps are bound to their existing independent cold records. The checker does not repeat the original finite censuses or attempt to prove them from scratch.

## Owned receipt

One owned 60-second arithmetic process performs these checks. Durable stage records contain elapsed time and current/peak memory. The child can write only a pending arithmetic report. After a timely successful exit, the owner rechecks the candidate, preparation, report, and stage bindings, then writes an `EXACT_COUNT_WITNESS` receipt. Late, failed, or incomplete execution cannot produce an accepted receipt through this path.

The receipt contains `accepted`, `count_feasibility_claimed`, `full_target_checks_passed`, and `restored_original_parent_checks_passed`, together with the candidate hashes and the explicit `acceptance_source_sha256`, `target_proto_sha256`, `model_preparation_sha256`, and `query_preparation_sha256`. It also binds the final 18,444 domains. The literal-lift intake must check this receipt and its source gate before attempting its separate construction.

## Frozen bindings and limits

The first source is bound to the completed first lightweight query, which returned no candidate. The separately named no-LP source changes only the query-preparation path and hash. All twelve functions are AST-identical; the binding control records the complete one-line substitution. The no-LP version binds preparation `123c940a34b590c944316a2fd606e5febcf1cedbdea3ec0f828d41b115068f37`.

Even a passed receipt certifies only the finite count and moment conditions. It does not certify a literal incidence, an exterior graph, all untested positive-semidefinite inequalities, or a Conway99 graph. This package contains no accepted receipt and makes no feasibility claim.
